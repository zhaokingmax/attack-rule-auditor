# attack-rule-auditor

**Version: 1.2** | Release Date: June 11, 2026

Defensive MITRE ATT&CK coverage-truth auditor for Linux, Containers, Kubernetes scenarios, and Network Devices.

The active package is intentionally scoped. It does not claim full Enterprise ATT&CK coverage, and it does not include Windows, macOS, SaaS, IaaS, Office Suite, ESXi, PRE, Mobile, or ICS platform packs.

## Run An Audit

```bash
python scripts/audit.py \
  --input ./rules \
  --mode folder \
  --platform "Linux,Containers,Network Devices" \
  --scenario container_escape \
  --index attack_data/index
```

With runtime and fixture context:

```bash
python scripts/audit.py \
  --input ./rules \
  --fixtures ./fixtures \
  --runtime-inventory ./runtime_inventory.json \
  --sensor-health ./sensor_health.json \
  --kernel-context ./kernel_context.json \
  --k8s-audit-policy ./k8s_audit_policy.json \
  --network-device-inventory ./network_device_inventory.json \
  --mode folder \
  --platform "Linux,Containers,Network Devices" \
  --scenario kubernetes_api_abuse \
  --index attack_data/index
```

Audit output is written under `.audit_runs/<run_id>/` unless `--output-root` is changed.

## Evidence Model

Coverage is not accepted from ATT&CK tags alone. A strong claim needs:

- Scenario denominator proof.
- Direct technique or sub-technique binding.
- Scenario behavior primitive binding.
- Data Component minimum-set support.
- Parsed condition evidence.
- Collector to parser to normalizer to rule to alert field-chain proof.
- Safe positive, negative, variant, and field-chain fixture requirements.
- Runtime and sensor context for Linux/container/Kubernetes/network-device telemetry.
- Defensive bypass-resilience proof requirements.

If any gate is missing, the claim stays conservative and the blocker is reported first.

## Remediation Output

Each audit now produces remediation artifacts:

- `remediation_plan.jsonl`: structured findings, defensive gap summary, required fields, validation requirements, and language-specific code-patch strategy.
- `remediation_plan.md`: blocker-first improvement plan for rule, parser, normalizer, collector, fixture, and runtime/sensor fixes.
- `patch_blueprints.jsonl` and `patch_blueprints.md`: language-specific defensive patch blueprints for C, C++, Java, Python, Rust, Go, YAML, Sigma, Falco, and auditd-style targets.
- `field_preservation_tests.jsonl` and `field_preservation_tests.md`: parser/normalizer regression metadata for required raw and normalized fields.
- `minimal_fixture_suite.jsonl` and `minimal_fixture_suite.md`: safe positive, negative, variant, and field-chain fixture requirements for the selected scenario.

For already claimed techniques, remediation resolves the concrete `file_path` and `rule_id` where possible. For uncovered techniques, it keeps the primary file unknown and reports `candidate_patch_files` so the user can decide whether to extend an existing rule, add a new rule, or update parser/normalizer code.

When the user explicitly asks for modified code, the skill should read the target source and provide or apply defensive changes in the current language and style. Supported code/review targets include C, C++, Java, Python, Rust, Go, YAML, Sigma, Falco, auditd, parser code, normalizer code, and collector code.

## Active Directory Layout

```text
<project-root>/
├── README.md
├── requirements.txt
├── scripts_manifest.json
├── attack_data/
├── evals/
├── schemas/
├── scripts/
└── utils/
```

Top-level responsibilities:

- `README.md`: human-facing usage and maintenance notes.
- `requirements.txt`: Python dependencies for the audit scripts.
- `scripts_manifest.json`: active runtime, maintenance, utility, archived, and experimental script classification.
- `attack_data/`: active ATT&CK index, scenario model, fixture templates, field aliases, scope lock, and sensor capability data.
- `evals/`: skill evaluation prompts for audit, remediation, and code guidance behavior.
- `schemas/`: JSON schemas used by validators and report checks.
- `scripts/`: audit orchestration, model maintenance, remediation planning, and coverage analysis tools.
- `utils/`: shared helper code used by the scripts.

There is no active Node/npm runtime requirement. Former `package.json`, `package-lock.json`, and `node_modules/` content is archived under `laji/`.

Generated reports are rebuildable outputs and should stay outside the active `attack_data/` package.

## Maintenance

Refresh the local ATT&CK index:

```bash
python scripts/build_attack_index.py enterprise-attack.json attack_data/index --scenario-map attack_data/models/scenario_seed_map.json
```

Refresh scope support artifacts:

```bash
python scripts/network_device_extension.py
python scripts/build_network_alias_pack.py
python scripts/build_scope_lock.py
```

Refresh and validate the model:

```bash
python scripts/scenario_model_lint.py --platform "Linux,Containers,Network Devices"
python scripts/scenario_attack_id_health.py --platform "Linux,Containers,Network Devices"
python scripts/build_depth_gap_backlog.py
python scripts/analyze_quality_strict.py
```

The active `scripts/` directory keeps audit runtime scripts and repeatable maintenance tools only. Historical one-time model generators and stale compatibility scripts are archived under `laji/scripts/`.

Run the engineering regression suite:

```bash
python scripts/verify.py
```

Useful engineering helpers:

```bash
python scripts/script_dependency_check.py
python scripts/package_check.py
python scripts/cache_status.py
python scripts/subtechnique_resolver.py
python scripts/retention_manager.py --dry-run
```

Compare two completed audit runs or rule packages:

```bash
python scripts/compare_rule_packages.py --a-run ./run_a --b-run ./run_b
```

## Safety Boundary

This repository is for defensive rule auditing and hardening. It may produce coverage blockers, safe fixture metadata, parser/normalizer changes, detection-rule improvements, and defensive code-patch guidance. It must not produce exploit payloads, weaponized commands, live abuse procedures, or operational bypass instructions.
